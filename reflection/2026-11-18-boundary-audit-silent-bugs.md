# 2026-11-18 一轮边界审计：四个「不报错但结果错」的坑

## 1. 假加速：改了 shader 的 tile，忘了 host 的 dispatch

**现象**：把 conv3x3_cm.comp 的 TW 从 32 改成 16 后，512x288 的 1.7m 从 13.26 fps 变成 20.97 fps，看起来 +58%。

**根因**：host 端 `src/nanovsr.cpp:1295` 和 `:1394` 的 dispatch 仍是 `(w + 31) / 32`，每组只覆盖 16 像素却按 32 像素切网格 —— 宽度方向只算了一半，输出当然快。同样的硬编码还在 `src/model_test.cpp:516`、`src/bench_model.cpp:422`。

**修法**：tile 参数统一成 `constexpr int CM_TW = 16, CM_TH = 8;`（`src/nanovsr.cpp:1027`），四处 dispatch 全部改成 `(w + CM_TW - 1) / CM_TW`；1x1 内核（`shaders/conv1x1_cm.comp`，TW=32/TH=4）有自己的一套，不能跟着改。

**教训**：性能数字必须先过「输出是否完整/逐位一致」这一关（644k kn_in 6 帧 crf0 的 md5 `4a7f365599279892c03c76ea01f8dcee` 是现成的闸门），否则测到的可能是「少干活」。

## 2. tile 比重叠还小 → 步长退化成 1 像素，切出上千块

**现象**：`nanovsr.exe --in tiny.mp4(98x62) --tile 32x32` → 「分块 2077 块」，0.66 fps（正常 1 块、210 fps），慢 300 倍。

**根因**：`grid_for()` 的步长是 `max(1, tw - ov)`；644k 的 ov=32，tw=32 → 步长 1，于是 98 列 × 21 行 = 2077 块。

**修法**：`src/nanovsr.cpp` 的 `grid_for()` 里强制 `tw >= min(W, ov+16)`、`th >= min(H, ov+16)`；手动 `--tile` 太小时直接忽略并退回自动分块（打印提示）；`--ov` 超过帧短边一半时收窄（否则小图同样爆炸）。

**教训**：所有「步长 = 尺寸 - 重叠」的网格算法都要对 `重叠 >= 尺寸` 设防，退化情形不会报错，只会变慢几百倍。

## 3. 静默成功：写失败、编码器退出码、零帧都不影响退出码

**现象**：`--out nodir\x.mp4`（目录不存在）返回 0；`--ffmpeg D:\nope\ffmpeg.exe` 也返回 0。脚本/CI 会以为成功。

**根因**：`src/nanovsr.cpp:1878` 原来无条件 `return 0`；`pclose_w(fout)` 的返回值被丢掉，写线程的 `wq_err` 只 printf。

**修法**：检查 `pclose_w(fout) != 0`、`wq_err`、`total <= 0` 三种情况，任一成立返回 1 并打印原因（编码器异常退出时还打印返回值）。

**教训**：只要程序会写文件，退出码必须反映「文件到底写成了没有」。

## 4. 旋转元数据：ffprobe 报旋转前尺寸，ffmpeg 解码已转正

**现象**：带 `rotate=90` 显示矩阵的手机竖拍视频，输出 3416x1920 的斜切花屏，且 rc=0、无任何警告。

**根因**：ffprobe 的 `width/height` 是旋转前的（854x480），ffmpeg 解码默认按显示矩阵转正（480x854）→ 帧尺寸与缓冲不符，逐帧切片全错位。

**修法**：探测 `stream_side_data=rotation`，命中 90/270 时交换 W/H 再继续（并打印「按 480x854 处理」）。修后同一素材输出 1920x3416，画面正确（不斜切）。

**教训**：外部工具报的尺寸和它吐出来的数据尺寸不一定是同一个坐标系 —— 凡是从 ffmpeg 管道读裸帧，都要确认两者一致。

## 顺带修的两条 UX

- `--gpu N` 越界时以前静默用默认设备，现在打印「--gpu 7 越界（本机共 2 个 Vulkan 设备）」；
